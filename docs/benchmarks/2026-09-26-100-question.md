# DOGA v1.2.0, matched 100-question classifier evaluation

This report measures the v1.2.0 behavior before the mode and fallback changes in v1.3.0. [Per-question results](2026-09-26-100-question-results.jsonl) are included as a JSONL fixture. The question labels were authored for an earlier Jev evaluation and reused without revising them for Laya.

## Decision

Do not activate Laya as the default decision classifier yet. Its local path functions, but this checkpoint and these questions performed materially worse than Jev on the authored labels. Keep the three modes conceptually separate: Jev through the API, Laya only, and Laya with Jev on local failure. The third mode is not a third classifier.

## Method and evidence boundary

The same 100 unique, generic questions from the earlier DOGA benchmark were replayed through DOGA v1.2.0's registered `pre_llm_call` hook in a fresh Hermes process. They cover 15 topics inspired by recurring Mnemosyne themes. The existing labels were authored before this Laya comparison, but they are subjective and not an independently adjudicated ground truth. The installed plugin's response-contract source matches the fork; the installed plugin also carries a local Mnemosyne compatibility bridge. Optional DOGA memory and De Bono guidance were disabled in this isolated process. The running gateway had not adopted the staged Laya environment settings, so this is a fresh-process demonstration, not a gateway-session test. No main-model final answers were scored.

Each question ran in three settings: Laya local with no fallback, Jev API, and Laya with Jev fallback enabled. Thus there are 100 prompts and 300 hook evaluations, not 300 different questions. The fallback setting calls Jev only on a Laya exception, not on a weak or inaccurate classification. All healthy local calls remained local. Raw case records include model, typed answers, contract, latency, and network route metadata, not credentials.

The paired Jev run used model `typesafe/jev-1.13-20260917`, with provider-reported cost $0.003025218 for 100 calls. Direct TypeSafe routing was not needed in this run. Laya used the local `laya-rl-agent` checkpoint with no provider request. The 100 Laya-only and Laya-with-fallback contracts were identical. Their exact contracts matched Jev in only 3 of 100 cases. Laya's saved choice temperatures triggered the upstream warning that some confidence values are uncalibrated.

## Diagnostic examples

* ID 3: The user asks whether to activate a plugin without a gateway or outage window. Laya chose `clarify`, but scored ambiguity 0.3499, yielding no focused question. Jev scored 0.80 and generated one. The same split occurs on the missing backup objectives in ID 22 and missing salary floor in ID 52.
* ID 13: The local versus OpenRouter routing decision omits privacy, latency, and budget. Laya chose `recommend`, ambiguity 0.5277; Jev chose `clarify`, ambiguity 0.85. DOGA consequently treated the former as a direct recommendation and the latter as a question.
* ID 28: An unauthenticated LAN dashboard without known network reachability was rated `low` stakes by Laya and `high` by Jev. The author's high-stakes label is defensible here, though the exact response mode is debatable.
* ID 20: A direct conceptual question about token prices was marked high ambiguity by Laya at 0.7722 and given a focused-question contract. Jev scored 0.18 and explained directly.
* ID 91: A trip request lacks its city, dates, and starting point. Laya chose `clarify` but scored ambiguity 0.213, so DOGA did not actually require a question. Jev chose `clarify` at 0.93.

Laya selected `mode=clarify` in 35 cases, but 32 of those had ambiguity below DOGA's 0.7 threshold, so the rendered contract did not require a question. It selected `high` stakes once, on ID 6, while the authored set has 13 high-stakes cases. Jev missed some cases too, including IDs 21 and 28. These are diagnostics against one authored test set, not population accuracy estimates.

## Recommendations and follow-up

The first three items were implemented in v1.3.0; calibration and downstream answer tests remain future work.

1. Make the public interface exactly three mutually exclusive modes: `jev_api`, `laya_local`, and `laya_with_jev_fallback`. Keep aliases for existing `/doga provider` and `/doga fallback` commands for compatibility, but display one effective mode and relabel `/doga jev on|off` as a response-contract toggle. Update README, help, and status so Laya is described as an alternative classifier and Jev as optional error fallback, not as an additive third provider.
2. Keep Jev API as the recommended default while Laya is uncalibrated. Do not activate the staged Laya-primary gateway settings without an explicit choice. The fallback mode only handles local load, inference, or schema errors; it does not catch confidently wrong local judgments. Describe that boundary prominently.
3. Remove the silent loss of local failure evidence by logging a bounded error category when a fallback occurs, without logging the request. Consider a circuit breaker so repeated local failures do not quietly turn every request into remote traffic.
4. Before changing the 0.7 threshold or inventing confidence-based fallback, improve or select Laya questions/checkpoints and assess them against an independently labeled held-out set. Merely lowering 0.7 on this set exchanges missed high ambiguity for many false alarms. Separately test the inconsistent `mode=clarify` plus no-question contract rather than forcing every Laya clarify mode into a question.
5. Add a matched downstream answer study after the classifier path is sound. Hook injection alone does not prove that Hermes follows a contract or gives better answers.

The v1.2.0 evaluation itself made no fork, documentation, installation, or gateway configuration edits. Its local failure and both Jev network routes were smoke-tested in the earlier installation work, but no Laya failure occurred in this 100-case run. The v1.3.0 release subsequently implemented the explicit modes, bounded error fallback, and documentation changes discussed here.
